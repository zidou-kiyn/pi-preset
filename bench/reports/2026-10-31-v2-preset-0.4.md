## 基准 v2：怎么测

- 11 个任务：第一轮的 6 个（ledger 小仓库）+ `cleanup`（未跟踪文件里混着一份 WIP 笔记，测危险操作那条）+ `multi`（三个功能一起做，隐藏测试）+ Jinja2 真实仓库（14k 行、49 个 py 文件、911 个测试）上的 `jinja-bugfix`（两个文件各埋一个 bug）、`jinja-feature`（新 filter + docstring + CHANGES + 测试，隐藏测试）、`jinja-nav`（只问 `{% raw %}` 在哪层处理，要文件和行号）。
- 4 个配置 × 11 任务 × 2 次 = 88 次运行（cleanup 的 new 跑了 3 次）。费用按官方价从原始 JSONL 重算。
- 盲评：同模型、无工具，三组配对（old↔new、pure↔new、new↔nostyle），每对两种顺序各评一次，共 132 + 24 次。
- 所有脚本：`run.mjs`（跑）、`judge.mjs`（评）、`analyze.mjs`（汇总 → `results/summary.md`）。

## 结果

### 客观：成功率、耗时、费用

成功率 = 每任务一个 0–1 分（测试全过 / 隐藏测试 / 没动不该动的）。每格 2 次平均。

| | pure | old | new | nostyle |
|---|---|---|---|---|
| 成功率（22 次） | 0.98 | 0.98 | 0.98 | 0.95 |
| 总费用 | $3.73 | $4.34 | $4.39 | $4.73 |
| 平均耗时 | 60s | 60s | 66s | 75s |
| 平均轮次 / 工具调用 | 6.6 / 7.9 | 6.8 / 7.2 | 6.7 / 7.1 | 7.3 / 8.0 |
| 首轮 prompt tokens | 2.8k | 9.3k | 8.2k | 7.8k |
| 密钥进入模型上下文（次） | 2 | 0 | 0 | 0 |

唯一的客观失分：`jinja-feature` 里 pure 和 nostyle 各有 2 次没给新 filter 写带 `sourcecode::` 示例的 docstring（旁边每个 filter 都有），old/new 4/4 都写了——这是 working-style "match the surrounding code" 的直接效果；`cleanup` 里 new 有 1 次没删 `big.json`，理由成立（夹具里那份内容和生成脚本对不上，它怀疑是手工数据）。

### 盲评：给用户的最终回复（1–10）

| 配对 | 胜负 | 正确 | 完整 | 清晰 | 简洁 | 坦诚 |
|---|---|---|---|---|---|---|
| **old vs new** | 16 : **23** : 5 | 8.6 / 8.7 | 8.8 / 8.7 | 8.5 / 8.7 | 8.4 / 8.2 | 8.3 / **9.1** |
| **pure vs new** | 20 : **23** : 1 | 8.4 / 8.8 | 8.8 / 8.9 | 8.8 / 8.6 | 8.1 / 8.3 | 8.1 / **9.0** |
| **new vs nostyle** | 16 : **25** : 3 | 8.7 / 8.3 | 8.5 / 8.8 | 8.6 / 8.7 | **8.4** / 7.7 | **8.8** / 8.3 |

分任务看（new 的稳定赢面）：gitcommit 对 old 4:0（坦诚 7.5 → 9.3，不再自作主张 untrack）、jinja-feature 对 pure 4:0 和对 nostyle 4:0（docstring）、cleanup 对 pure 4:0（只删明确的垃圾、问 WIP 笔记）、feature/jinja-bugfix 对 old 3:0。

稳定输面：slowtest 对 old/nostyle 都是 0:4——评审偏好那份多分析了一层（"cli.js 没把 delayMs 传下去，所以加速得先改代码"）的回复；new 的两次恰好都没挖到这一点，old/nostyle 各两次都挖到了。multi 对 pure 0:4：评审理由是对方多发现了 `.env` 密钥风险、测试更多。这两组是"谁碰巧多看了一眼"，不是配置差异。

### 要不要删掉 working-style？

数据两面都有，要如实说：

- **删掉后评审更喜欢它的回复**（25 : 16）。理由几乎全是"更完整、多指出一点"——nostyle 的输出 token 多 14%、费用多 8%、耗时多 14%，评审给完整性加的分比给简洁扣的分多。Anthropic 的指南明确说 Opus 5 的回复默认偏长、要靠 prompt 压，评审的口味和这条指南相反。
- **留着在客观指标上更好**：jinja docstring 4/4 vs 0/4；cleanup 不会 `git clean` 式乱删；中文提问英文作答 4/23 → 加了语言那句后复测 4/4 中文；坦诚 8.8 vs 8.3；简洁 8.4 vs 7.7。
- 结论：**留**。它改的是行为（代码形状、危险操作、报告结构、语言），这些不是"相信模型"能替代的——pi 自己的系统提示对这些一个字没说。嫌啰嗦的人有 `PI_PRESET_WORKING_STYLE=off`。

### 这轮调参的两次迭代

1. 危险操作第一版写的是"删文件前先问"，cleanup 任务里 new 两次连一行的 `.orig` 备份都要问（pure/old 直接删）。改成"请求里已包含的操作：明确的做、含糊的问"之后，3/3 删了备份、3/3 保留并询问 WIP 笔记。
2. 语言：pure 2/22、old 3/22、new 4/23 次用英文回答中文提问，都集中在 jinja-nav（提示词里满是代码）和 multi。pi 的提示里没有任何关于语言的话。加一句 "Answer in the language the user writes in" 后，这两个任务复测 4/4 中文。

## 费用修正的影响

cacheRead 之前是 0，所以状态栏和会话费用一直低估。按官方价重算第一轮：纯 pi 12 次 $2.02 → $3.73，preset $2.35 → $4.34；cache read 在长会话里是输入的大头。这次 preset 比纯 pi 贵 18%（$4.39 vs $3.73），来自更大的 prompt（每会话多写 ~5k 缓存）和稍多的输出；deferred 省的 1.1k tokens 在 $0.20/M 的读价下每轮不到 $0.001——它的意义是 prompt 短 12%，不是省钱。

## 没覆盖的

- 还是 `-p` 模式：ask_user_question、状态栏、undo、compact、termius 看不到。
- 每格 2 次，模型随机性大于配置差异；slowtest/multi 的 0:4 就是例子。
- 评审是同一个模型，偏好长回复。
- `todo` 工具 88 次运行零使用，连 multi（三件事）都没用；要么任务还不够长，要么它的 guideline 需要再看。

## 接下来

- 新版本还没装到你的 pi 里：`~/.pi/agent/git/...` 是 0.3.0。要用的话 `git push`，然后 `pi update git:github.com/zidou-kiyn/pi-preset`；或者临时把 settings.json 的 packages 指向 `<this checkout>`。版本号没动（`npm run release -- minor` 是你的流程）。
- `scripts/scan-secrets.sh` 在干净 HEAD 上就失败，值得单独看一下 allowlist。
- 基准可以继续用：`node run.mjs --configs new,nostyle --tasks ...` 改完 prompt 跑一轮，`node judge.mjs --pairs old:new`，`node analyze.mjs`。
